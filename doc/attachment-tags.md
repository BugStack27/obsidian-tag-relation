# 附件标签 - 可行性与方案

## 1. 问题与现状证据

| 位置 | 现状 |
|------|------|
| `src/view.ts:119-127` | `file-open` 跟随 `getActiveFile()`，附件与 Canvas 也会进入面板 |
| `src/view.ts:289-316` | 只按「笔记」解释：无标签就提示「在正文或属性中添加 #标签」，但附件没有可编辑的正文和属性 |
| `README.md:57` | 文档写「非 Markdown 完全跳过」，与附件打开后仍会刷新面板的实际行为不完全一致 |

**结论先行**：文案问题本轮已修（附件/图片/Canvas/音视频各自给出「不是 Markdown 笔记」的说明）；「给附件打标签」不建议用插件私有索引实现，若要做，推荐**单一索引笔记**方案（见第 4 节），并且应先由用户确认是否值得承担它的代价。

## 2. 前提约束（决定方案边界）

- Obsidian 的属性就是 Markdown 文件顶部的 YAML frontmatter（官方帮助 Properties 页），二进制附件没有可写的属性字段；`.canvas` 是 JSON，也不是可用标签的载体。
- 因此附件标签只能落在三类地方：插件自己的存储、vault 里的 JSON、vault 里的 Markdown 文件。
- Obsidian 的标签面板、`tag:` 搜索、关系图谱只认识 Markdown 里的标签。插件若自造标签，就必然与这些原生能力割裂——这是所有方案共同的产品代价。
- 本插件当前聚合方式：`computeRelationGroups` 遍历 `vault.getMarkdownFiles()`，从 metadata cache 取标签。要纳入附件，需要额外提供「附件 → 标签」来源。

## 3. 方案对比

| 方案 | 存储 | 聚合 | 编辑 | 重命名/删除 | 同步与重装 | 与 Obsidian 生态 | 评价 |
|------|------|------|------|-------------|------------|------------------|------|
| A. 插件 `data.json` | 路径 → 标签 | 面板内合并 | 面板内新增编辑器 | 靠 vault rename/delete 事件维护，外部改动会丢 | 重装即丢；不进 vault 同步（除非同步 .obsidian） | 完全割裂 | 最省事也最脆，**不推荐** |
| B. vault 内 JSON 索引（如 `附件索引.json`） | 路径 → 标签 | 面板内合并 | 面板内编辑器 | 同上，路径键对移动敏感 | 随 vault 同步 | 割裂，JSON 在 Obsidian 里只是普通文件 | 技术上可行，但只是把 A 的脆弱点挪个位置 |
| C. 单一索引笔记 | 一行一条：`- [[file.pdf]] #标签` | 解析该笔记的 links + tags，按行配对 | 面板改行，或直接手改笔记 | Obsidian 自动更新 wikilink，天然跟随重命名 | 是普通笔记，同步、可 diff、可手改 | 标签是原生标签（会出现在标签面板/搜索里），但索引笔记本身必须被排除出关系结果 | **推荐（若要做）** |
| D. 每附件一个 sidecar 笔记 | 隐藏不了，只能是普通目录 | 天然参与现有聚合 | 编辑 sidecar | 链接自动更新 | 同步，但文件数量翻倍 | 标签天然原生，但关系面板列出的会是 sidecar，需要额外映射回附件 | 备选，文件数膨胀明显 |

## 4. 推荐方案：单一索引笔记

### 4.1 数据格式

一个普通 Markdown 笔记（路径可配置，默认如 `附件标签.md`），一行对应一个资源：

```markdown
- [[报告.pdf]] #工作/报告 #2026
- [[截图 2026-11-16.png]] #设计/参考
```

- 标签用行内 `#tag`，不需要新语法；用户可以直接手改，也可以被模板/脚本处理。
- 链接用 `[[完整路径]]` 而不是只写文件名，避免同名附件（`a/报告.pdf` 与 `b/报告.pdf`）解析到错误目标。

### 4.2 聚合

- 不清空重扫全库：只对索引笔记一次 `metadataCache.getFileCache(indexNote)`，取 `links` 与 `tags`，各自带 `position.start.line`，**按行号配对**即可得到「附件 → 标签」。不用手写 Markdown 解析。
- 用 `metadataCache.getFirstLinkpathDest(link, indexPath)` 把链接解析成 `TFile`；解析不到就视为悬空行。
- `computeRelationGroups` 增加一个可选的「额外资源标签」参数（附件路径 → 标签集合），并把索引笔记自身排除在结果之外，否则它会在每个分组里出现。
- 关系面板里附件行的打开方式沿用 `openFile`；摘要功能对附件跳过（当前 80 字摘要是按笔记正文取的）。

### 4.3 编辑

- 当前笔记是附件时，空态不再只是「不是 Markdown 笔记」，而是说明 + 「编辑标签」入口：输入标签后重写索引笔记中对应那一行。
- 写入用 `vault.process(indexNote, ...)` 原子修改；行不存在则追加。只改该行的标签段，保留用户手写的其它文字。
- 重命名：依赖 Obsidian「自动更新内部链接」设置，链接跟着改，无需自建 ID 映射；删除附件留下悬空行，面板可提示并提供一键清理。

### 4.4 必须接受的代价

1. 索引笔记在标签面板与 `tag:` 搜索里会带着全部附件标签出现，且点击标签会落到索引笔记而不是附件。
2. 索引笔记必须被插件排除在关系结果之外，属于插件内的特殊约定。
3. 附件本身的标签不参与 Obsidian 原生搜索（`tag:` 命中的是索引笔记）。
4. 用户需要接受 vault 里多一个索引笔记，或至少接受它的可配置路径。

## 5. 结论与建议

- **本轮不做附件标签**：需求里「给我一个方案，判断这个怎么做」的答案就是上面这份评估。附件标签不是补一段逻辑，而是引入一个新的数据源和一套编辑 UI，且必然与 Obsidian 原生标签体系部分割裂，值得先确认用户是否接受第 4.4 节的代价。
- **若确认要做**，按 C 方案分三步：① 索引笔记解析 + 聚合接入（含排除索引笔记）；② 附件空态里的标签编辑入口；③ 悬空行提示与清理。估算 1.5–2 个工作日（含审查），不需要新增依赖。
- **不建议** A/B 两种私有存储：路径键在移动/同步冲突时容易失配，数据不在笔记里，重装或换设备就可能丢，而且标签对 Obsidian 其余部分完全不可见。

## 6. 与本次改动的关系

本次只修「打开附件时的误导性提示」：

- `src/view.ts` — 新增 `describeNonNoteFile` 与 `renderNonNote`，非 Markdown 文件显示「当前打开的是 PDF 文件 / 图片 / Canvas 文件 / 音频 / 视频，不是 Markdown 笔记」，并说明标签关系只统计 Markdown 笔记。
- `README.md` — 修正「非 Markdown 完全跳过」的表述。
- 不触碰 `computeRelationGroups`、忽略标签语义、附件打开行为。
